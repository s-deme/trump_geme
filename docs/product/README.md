# 製品開発管理

ルール検証基盤の完成後に進めるUnity製品層のロードマップ、マイルストーン、設計判断を管理する。
ゲームルールの正本は引き続き`docs/rules/`とし、このディレクトリでは製品として遊べる状態へ
到達するための順序と完了条件を扱う。

## 正本

- [製品ロードマップ](roadmap.md)：優先順位、依存関係、現在地
- [M01 構造化表示契約](milestones/M01-structured-presentation.md)：現在のマイルストーン
- [設計判断記録](decisions/README.md)：後から覆すコストが高い判断

進捗状態は`Backlog`、`Ready`、`In Progress`、`Blocked`、`Done`の5種類とする。
同時に`In Progress`にできるタスクは1件だけである。

## Codexでの進め方

通常の1タスク実行では、次の依頼でロードマップ上の`Ready`最上位を選択する。

```text
ロードマップに従って続けて。現在のマイルストーンにあるReadyの最上位タスクを実装し、
完了条件を満たしたら進捗更新、必須検証、commit、pushまで行って。
仕様判断が必要な場合だけ止まって確認して。
```

複数タスクを連続して進めるときは、開いたバックログ全体ではなく、完了条件が明確な
1マイルストーンをCodexのGoalにする。

```text
/goal docs/product/milestones/M01-structured-presentation.md を実装し、
すべての完了条件と必須検証を満たすまで進める。
既存CLI互換性を維持し、各チェックポイントでロードマップを更新する。
```

Goalは目的、停止条件、参照ファイル、検証方法を明示する。OpenAIの
[Follow a goal](https://learn.chatgpt.com/use-cases/follow-goals)も、無関係な作業一覧ではなく
検証可能な単一目標とチェックポイントを定義する運用を推奨している。

## 更新規則

1. 着手前に対象タスクを`In Progress`へ変更する。
2. 対象タスクの範囲外を同じ変更へ混ぜない。
3. 重要な前提変更は`decisions/`へADRとして記録する。
4. 完了条件と必須検証をすべて満たした後だけ`Done`へ変更する。
5. 完了後、依存関係を満たした次のタスクを`Ready`へ変更する。
6. マイルストーン完了時はロードマップの現在地と完了日を更新する。

Markdownと`AGENTS.md`だけを変更した管理文書タスクは、`git diff --check`、文書内リンク、
状態遷移の整合性を検証すればよい。Runtime、プロジェクト設定、テスト、検証スクリプトへ
変更がある実装タスクは`AGENTS.md`の通常の必須検証に従う。
